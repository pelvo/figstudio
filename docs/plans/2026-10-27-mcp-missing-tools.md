### 2026-10-30T192120Z browser-step-guard
- What changed and how it was checked: in WebKit a sandboxed frame runs on the page's thread, so a shader that never returned blocked the whole tab, the frame-replacing timer included (seen in Playwright's WebKit: `page.evaluate` no longer answered). The browser module now calls a step counter at the start of every loop body and function body (inserted by oxc into main.ts before its types are stripped); past 20 million steps every further iteration or call throws, so a `catch` cannot keep it going. The counter and its reset (called by the bridge before each run) are named by a hash of the source, so the code cannot name them. A worker inside the sandboxed frame was tried first: Chromium gives it no WebGPU and WebKit does not start it. Tests: inserted calls on every loop and function kind, the 12 playground shaders still parse, endless loops and recursion with catch stop on the counter in Boa (each seen failing without the inserted calls); e2e in Chromium and WebKit (macOS): the real shader draws, an endless one stops with "step limit" and the page answers within 3 ms; the repo's shaders.spec gains that case. Also checked: Chromium in a Linux container draws shaders on its software WebGPU and stops the endless one.
- Not verified: Firefox (Playwright's Firefox does not start on this Mac, and headless Firefox in a Linux container has neither WebGL2 nor WebGPU, so the app does not start there, as on main); a native built-in that loops by itself (for example `forEach` over a huge empty array-like) is not counted and still relies on the frame being replaced after 10 s, which WebKit cannot do while it runs.
